# Claude 官方界面设计思想

本文把 Claude 产品界面中值得迁移的设计思想沉淀为设计判断，供后续页面改造和新页面设计使用。参考资料来自用户提供的 [`Caho1/open-claude-ui`](https://github.com/Caho1/open-claude-ui)，重点阅读其设计哲学、交互指南、组件实现和会话流文档。

**来源口径：**本文记录的是 Claude 官方产品呈现出的设计语言与交互取向。`open-claude-ui` 是对官方客户端进行逆向整理的第三方仓库；它能提供丰富的产品观察和可读实现，但其中的具体 token、算法参数及“官方内部实现”说法仍须按版本和官方蓝本核对。官方 UI kit 与官方指南中的精确值，以 [`anthropic-mcp-apps-design.md`](anthropic-mcp-apps-design.md) 为准；这份笔记用于指导设计判断，不取代精确 token 表。

## 设计原则

| 原则 | Claude 界面呈现出的做法 | 设计时要问的问题 |
|---|---|---|
| 温润的人文感 | 以暖中性色和克制的品牌陶土色建立气质；减少冷硬、高饱和的装饰色 | 颜色是否帮助内容阅读和状态辨识？品牌色是否只落在真正需要强调的地方？ |
| 用表面建立空间 | 通过相邻表面的细微明度差、低对比边界和柔和层次组织侧栏、画布、卡片、输入区和浮层 | 是否能先用表面和留白表达层级？只有层级不清时才加线框或阴影？ |
| 边界保持克制 | 独立对象用一个清楚的外边界；容器内部更多依靠间距、文字层级、轻背景或单向分隔线，避免连续套框 | 视线从页面到操作控件，是否被多层闭合边框切碎？内部控件是否可以改成无边框态？ |
| 几何服从角色 | 圆角随按钮、面板、消息气泡、输入框等角色变化；相邻嵌套形状的曲率和内边距彼此协调 | 这个组件的功能与层级是什么？圆角是在表达角色，还是全局套了一个值？ |
| 动效回应操作 | 按压、悬停、展开、拖动和吸附都有轻微反馈；位移与弹性服务于动作确认和空间连续性 | 动效是否让操作结果更容易感知？是否会拖慢阅读、抢走焦点或制造无意义的装饰？ |
| 尊重用户的阅读位置 | 流式生成时，只有用户仍停留在底部附近才跟随新内容；用户主动上滚后，系统让出视口 | 用户正在读历史内容时，界面是否仍在自动滚动？何时应显示“回到底部”提示而不是强制跟随？ |
| 为真实输入场景兜底 | 输入框兼顾中文等输入法的组合输入、附件和多行编辑；确认候选词的 Enter 不应误发送 | 键盘行为是否会打断 IME 组合输入？输入变高、附件增多或发送失败时状态是否清楚？ |
| 过程状态可理解 | 将等待授权、运行中、完成、失败等状态明确呈现；思考或工具过程的展开收起跟随任务状态 | 用户能否看懂系统正在做什么、需要自己做什么、失败后如何继续？ |
| 空间操作保持连续 | 媒体缩放围绕指针锚点变化；分栏拖动有约束、吸附和可恢复行为 | 操作前后用户关注的对象是否还留在原处？拖动是否有明确范围、键盘替代和复位方式？ |
| 复杂内容仍可读可达 | 对长消息、代码、侧栏窄宽、键盘焦点和实时数字等情况做适配，而不是只设计静态首屏 | 在窄容器、键盘操作和连续更新下，层级、焦点和读数是否稳定？ |

## 落地顺序

1. **先判断任务和状态。** 明确界面是在等待输入、生成、授权、展示结果还是恢复错误。
2. **再组织层级。** 先定画布、面板、内容和操作区之间的表面关系，再定边界、字体和形状。
3. **为交互写出状态变化。** 说明触发条件、反馈、取消/恢复路径，以及用户操作何时优先于自动行为。
4. **精确数值按来源落表。** 官方 UI kit / 指南有数值就优先引用；没有时可将本仓库提到的实现作为候选，标明“社区逆向参考”或“自定”，并在目标界面验证。
5. **检查内容和输入边界。** 至少检查长回答、流式追加、中文输入法、键盘焦点、窄容器、失败状态和深浅主题。

## 方法论教训

1. **学产品规律，别背孤立数字。** 一个圆角、弹簧或遮罩值只有放回组件角色、状态和上下文中才有意义。
2. **把自动化的权力交还给用户。** 自动跟随、自动展开和动画都要在用户主动操作时让路。
3. **先解决边缘场景，再润色反馈。** 输入法、长内容、键盘操作和错误恢复属于界面设计本身，不是实现阶段的补丁。
4. **分开原则与取值出处。** Claude 的产品设计语言可作为方向；仓库逆向得到的实现细节不能替代官方 Figma / 指南的精确 token。
